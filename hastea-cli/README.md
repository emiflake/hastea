# hastea-cli

The `hastea` command builds Hastea applications, and runs them during development with live reload.

```bash
hastea build [APP...]   # compile, and put the page together in dist/APP, ready to be served
hastea dev [APP]        # serve the page on http://localhost:8080, reloading it whenever the source changes
```

Both read `hastea.yaml`, looked for in the current folder and the folders above it. Without `APP`, they use the default application.

## Installing

The command runs on the machine you develop on, so it is built with an ordinary GHC (9.6 or later), not the wasm cross-compiler. Build it in a shell where `~/.ghc-wasm/env` has **not** been sourced: that file points `CC` and `LD` at the wasm C toolchain, which breaks native packages such as `network`.

```bash
cd hastea-cli
cabal install
```

That puts `hastea` in `~/.local/bin`. To run it without installing, use `cabal run -v0 hastea -- dev` from `hastea-cli/` (it finds the `hastea.yaml` above).

It needs the wasm toolchain from [ghc-wasm-meta](https://gitlab.haskell.org/haskell-wasm/ghc-wasm-meta) to do anything. If `wasm32-wasi-cabal` is not on your `PATH` but `~/.ghc-wasm` exists, the command uses the programs there by itself, so you do not have to source `~/.ghc-wasm/env`.

On Windows, all of this runs inside WSL; see the repository's README.

## hastea.yaml

```yaml
default: todomvc                     # the application to use when none is named

apps:
  todomvc:
    executable: hastea-todomvc       # the cabal executable (required)
    www: examples/todomvc/www        # its page: index.html, styles, images (optional)
    out: dist/todomvc                # where hastea build puts the page (default: dist/NAME)
    run: main                        # what hastea dev runs after every reload (default: main)
    optimize: false                  # shrink the module with wasm-opt in hastea build (default: false)

toolchain:                           # the programs to use, if not these
  cabal: wasm32-wasi-cabal
  ghc: wasm32-wasi-ghc
  node: node
  wasm-opt: wasm-opt

dev:
  port: 8080
  watch: [.]                         # folders to look for changes in
  ignore: [dist-newstyle, dist, node_modules, .git]
```

Paths are relative to the folder of `hastea.yaml`. A setting that is not listed here is reported, since it is most likely a typo. `default` can be left out when there is only one application.

## hastea build

Builds the executable with `wasm32-wasi-cabal build`, then puts in the output folder:

- `hastea.wasm`, the compiled module (made smaller with `wasm-opt -Oz` when `optimize` is set, or with `--optimize`);
- `ghc_wasm_jsffi.js`, the JavaScript that the module's FFI imports, generated by GHC's post-linker;
- `browser_wasi_shim.js` and `index.js`, which load the module and start it; they are built into the command (see [runtime/](runtime/README.md));
- the files from `www`. An application can bring its own `index.html` and `index.js`; without them it gets a default page with an element `main-node`, where `Hastea.App.runApp` shows the view.

The page needs nothing from any other host. Serve the folder with any static file server, for example `python3 -m http.server -d dist/todomvc 8080`.

`--out DIR` puts the page elsewhere. The output folder is emptied first, unless it holds files that are not from an earlier build.

## hastea dev

Runs the application in GHCi's browser mode (`-fghci-browser`): GHCi runs in the terminal, while its interpreter and the application run in the page. Changing a module and reloading takes well under a second, since nothing is linked.

1. The command starts `wasm32-wasi-cabal repl exe:EXECUTABLE` in browser mode, and serves the application's page on `http://localhost:8080`.
2. The page asks for a GHCi session and boots GHCi's interpreter in itself. GHCi loads the modules there, and the command runs `run`.
3. Whenever a Haskell file changes, the command runs `:reload` and then `run` again. Mounting replaces whatever an earlier run mounted in the same place (`Hastea.Root.mount` unmounts it first), so the page shows the new code. The state of the application starts over.
4. A changed stylesheet in `www` is replaced in the page. Any other change in `www`, to a `.cabal` file, `cabal.project` or `hastea.yaml` loads the page again with a new session.

Compilation errors are shown on the terminal and over the page until a reload works. The application's own output (`putStrLn`, `Debug.Trace`) goes to the browser's console.

Things to know:

- **One page at a time.** A GHCi session serves a single page. Loading the page again, or opening it in another tab, starts a new session (in about two seconds), and the old page stops working. A page that is open when `hastea dev` restarts loads itself again.
- **`run` and `foreign export`.** The `Main` module of an application usually has `foreign export javascript "hs_start" main`, for the built page to call. When GHCi reloads such a module, the browser's console shows errors about duplicate symbols (sometimes for modules with `foreign import javascript` too); the reload still works. Pointing `run` at a function in another module (`run: Example.TodoMVC.TodoMVC.runTodoMVC`) means `Main` is only reloaded when you edit it.
- **The page needs the internet.** In browser mode, GHC's loader fetches its WASI shim from esm.sh. A built page does not.
- **Browsers.** GHCi's browser mode works in Chrome and Firefox, but not in Safari or other WebKit browsers.
