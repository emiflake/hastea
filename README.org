#+TITLE: Hastea web framework
#+DESCRIPTION: A tasty hasty framework

* Fun with WebAssembly
  The Elm Architecture is a wonderful means for creating web apps without worrying about runtime errors, Hastea is a TEA-inspired web framework using those principles on top of Haskell compiled to WebAssembly with [[https://ghc.gitlab.haskell.org/ghc/doc/users_guide/wasm.html][GHC's WebAssembly backend]].

  (Hastea originally targeted Asterius, which has since been superseded by the wasm backend in mainline GHC.)

* Layout
  | ~hastea-html/~      | The ~hastea-html~ sublibrary: HTML elements, attributes, events, decoders, rendering and diffing. Pure Haskell |
  | ~hastea-component/~ | The ~hastea-component~ sublibrary: components, commands and subscriptions. Pure Haskell, builds on ~hastea-html~ |
  | ~hastea-core/~      | The ~hastea~ library: the runtime that puts views on the page (~Hastea.App~, ~Hastea.Root~, ~Hastea.Time~, ...)   |
  | ~examples/todomvc/~ | The TodoMVC example executable, with its static files in ~www/~                                              |
  | ~examples/ReactComparison/~ | Examples from the React documentation rewritten with Hastea, and a table of the differences ([[file:examples/ReactComparison/README.md][README]]) |
  | ~benchmark/~        | A table of rows written with Hastea and with React, and a script that measures both ([[file:benchmark/README.md][results]]) |
  | ~build.sh~          | Builds the example into ~dist/~                                                                              |

* Writing views
  ~hastea-html~ has a function for every element of the HTML standard, plus their attributes and events. It is a sublibrary of the ~hastea~ package, which re-exports the modules of its sublibraries, so depending on ~hastea~ is enough. (To use it alone, for example to render views on a server, depend on ~hastea:hastea-html~.)

  #+BEGIN_SRC haskell
  import Hastea.Html (Html)
  import Hastea.Html qualified as H
  import Hastea.Html.Attributes qualified as A
  import Hastea.Html.Events (onClick, onInput)

  view :: Model -> Html Msg
  view model =
    H.div
      [A.className "signup"]
      [ H.input [A.placeholder "Your name", A.value model.name, onInput NameChanged]
      , H.button [onClick Submit, A.disabled (null model.name)] [H.text "Sign up"]
      ]
  #+END_SRC

  | ~Hastea.Html~            | Elements. Void elements such as ~input~ and ~br~ take only attributes                         |
  | ~Hastea.Html.Attributes~ | Attributes, and helpers such as ~classList~, ~styles~, ~dataAttr~ and ~aria~                  |
  | ~Hastea.Html.Events~     | Event handlers; ~on~ and ~onWith~ for custom ones                                             |
  | ~Hastea.Html.Decode~     | Decoders for reading event data                                                               |
  | ~Hastea.Html.Render~     | ~renderHtml~, which turns a view into a string of markup, for tests and server-side rendering |
  | ~Hastea.Svg~, ~Hastea.Svg.Attributes~ | SVG elements and attributes, to import qualified                                 |

  ~fragment~ puts several nodes where one is expected, without an element around them.

  Import elements and attributes qualified, as ~H~ and ~A~. There is an element for every tag, including ~a~, ~i~, ~div~, ~title~ and ~time~, and several names are both an element and an attribute; qualified, none of them get in the way of your own names or of the ~Prelude~. Event handlers do not clash with anything and read well unqualified.

* How rendering works
  The design follows React, and leans on purity where Haskell allows more.

  - *Rendering is split into a pure and an effectful half.* ~Hastea.Html.Diff.diff~ compares the tree on the page with the new one and returns a ~Patch~: a description of what to change. Only ~Hastea.Internal.Commit~ touches the DOM, by carrying the patch out. The pure half is tested without a browser.
  - *Event handlers are data, not DOM listeners.* Nothing is attached to the elements of a view. The root listens for each kind of event once; when one arrives it locates the target in the tree it last rendered and runs the handlers found there and on its ancestors. Handlers can therefore never be out of date, and changing one costs nothing.
  - *Renders are batched.* Messages update the model immediately, but the view is shown at most once per frame.
  - *~keyed~* gives a child an identity, so that reordering or filtering a list moves DOM nodes instead of rebuilding them.
  - *~lazy~* skips a subtree whose inputs are the same values in memory as last time. Because views are pure this is always safe, and the skipped view is not even computed.

  ~Hastea.App.runApp~ is the Elm-style loop (model, update, view). It is a thin layer over ~Hastea.Root~ (~mount~ and ~render~), which shows trees, keeps the state of the components in them, and reports messages. It can serve as the base for other architectures.

* When something goes wrong
  A view or an update function that fails does not take the page down: the failure is written to the browser console as an error and the page stays as it was, because a view is computed completely before anything on the page is changed. Likely mistakes are written to the console as warnings, each one once: two children with the same key, a fragment directly inside ~lazy~, and an event that its handler could not read.

* Components
  A view can contain /components/ (~Hastea.Component~, in the ~hastea-component~ sublibrary): parts that keep their own state, as in React. A component is made of pure functions, and ~use~ places it in a view. Whatever shows the view keeps the state, one per place the component is used in.

  #+BEGIN_SRC haskell
  counter :: Component () Int Msg out
  counter = component initial update view
   where
    initial () = 0
    update Pressed count = (count + 1, [])
    view () count = H.button [onClick Pressed] [H.text (show count)]

  page :: Html msg
  page = H.div [] [use counter (), use counter ()] -- two counters, counting separately
  #+END_SRC

  The first type parameter is what the component is given by its surroundings (its props) and the last what it reports back: ~update~ returns ~[Emit value]~, and the user turns that into one of its own messages with ~<$>~. ~update~ can also ask for a command with ~[Run command]~. A component can have subscriptions, and can ask for effects when it appears or goes away: ~(component initial update view){subscriptions, onMount, onUnmount}~. In a list, ~keyed~ makes the state follow the item.

  Components and ~runApp~ mix freely: use one model for what the whole application shares and components for what is local. See [[file:examples/ReactComparison/README.md][examples/ReactComparison]] for a page built only from components, and ~examples/todomvc~ for one built only on a model.

* Effects
  ~update~ is pure. To make something happen outside the model it returns a /command/ (~Hastea.Cmd~) next to the new model; the runtime runs it and feeds any resulting message back into ~update~. To receive messages that do not come from the view, an application declares /subscriptions/ (~Hastea.Sub~) as a function of its model; the runtime starts and stops them as needed.

  #+BEGIN_SRC haskell
  update :: Msg -> Model -> (Model, Cmd Msg)
  update msg model = case msg of
    Saved -> (model{saving = True}, Time.after 1000 SaveFinished)
    SaveFinished -> (model{saving = False}, Dom.focus "name-field")
    Ticked now -> (model{time = now}, Cmd.none)

  subscriptions :: Model -> Sub Msg
  subscriptions model
    | model.clockVisible = Time.every 1000 Ticked
    | otherwise = Sub.none

  main :: IO ()
  main = run (app update initial view){subscriptions = subscriptions}
  #+END_SRC

  | ~Hastea.Cmd~  | ~none~, ~batch~, ~perform~ (run ~IO~ and send the result), ~effect~, ~custom~ |
  | ~Hastea.Sub~  | ~none~, ~batch~, ~custom~                                                   |
  | ~Hastea.Time~ | ~now~, ~after~ (commands) and ~every~ (subscription)                        |
  | ~Hastea.Dom~  | ~focus~, ~blur~                                                             |
  | ~Hastea.Http~ | ~get~, ~getJson~, ~request~, ~requestJson~                                  |
  | ~Hastea.App~  | ~runApp~ for the simple case; ~App~, ~app~ and ~run~ for the rest; ~runView~ for a page of components |

* Building
** Get the wasm toolchain
   You need the ~wasm32-wasi-ghc~ cross-compiler and ~cabal~ from [[https://gitlab.haskell.org/haskell-wasm/ghc-wasm-meta][ghc-wasm-meta]]. Either:

   - With Nix:
     #+BEGIN_SRC bash
     nix shell 'gitlab:haskell-wasm/ghc-wasm-meta?host=gitlab.haskell.org'
     #+END_SRC
   - Without Nix (x86_64/aarch64 Linux, macOS):
     #+BEGIN_SRC bash
     curl https://gitlab.haskell.org/haskell-wasm/ghc-wasm-meta/-/raw/master/bootstrap.sh | sh
     source ~/.ghc-wasm/env
     #+END_SRC
     The script needs ~curl~, ~jq~, ~unzip~, ~zstd~ (for ~unzstd~), ~xz~, ~make~ and a C compiler; it stops partway if one is missing, and can simply be run again. On Debian/Ubuntu:
     #+BEGIN_SRC bash
     sudo apt-get install curl jq unzip zstd xz-utils make gcc
     #+END_SRC
     It installs into =~/.ghc-wasm=. Run ~source ~/.ghc-wasm/env~ in every new shell to put the tools on your ~PATH~.

   Both routes download prebuilt binaries from GitHub releases, so they need access to ~github.com~ as well as ~gitlab.haskell.org~.

   Hastea is tested with the GHC 9.14 flavour.

** Build, test and run
   Everything is one cabal package (~hastea.cabal~), built with ~wasm32-wasi-cabal~, the cabal wrapper that comes with the toolchain:

   #+BEGIN_SRC bash
   wasm32-wasi-cabal test               # build everything and run the tests
   ./build.sh                           # build TodoMVC into dist/ (or: ./build.sh react-comparison)
   python3 -m http.server -d dist 8080  # then open http://localhost:8080
   #+END_SRC

   The tests cover the two pure sublibraries, ~hastea-html~ and ~hastea-component~, and run under ~wasmtime~, which is part of the toolchain.

   The example page fetches [[https://github.com/bjorn3/browser_wasi_shim][browser_wasi_shim]] from jsDelivr when it loads, so the browser needs internet access.

   If you have your own ~cabal~ on your ~PATH~ it works in place of ~wasm32-wasi-cabal~, since ~cabal.project~ selects the wasm compiler; for the example, run ~CABAL=cabal ./build.sh~.

* Development
  - Formatting: [[https://github.com/fourmolu/fourmolu][fourmolu]], configured in ~fourmolu.yaml~.
    #+BEGIN_SRC bash
    fourmolu -i hastea-core hastea-html hastea-component examples
    #+END_SRC
  - Editor support: ~hie.yaml~ points HLS at the cabal components. HLS has to be able to load the project with the wasm compiler for this to work.
  - The code builds warning-free under ~-Wall -Wcompat~.
  - Records use ~OverloadedRecordDot~ (~model.name~), with ~NoFieldSelectors~ and ~DuplicateRecordFields~, all enabled in ~hastea.cabal~. Fields are therefore not functions, and can share names with each other and with HTML elements.
