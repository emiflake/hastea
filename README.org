#+TITLE: Hastea web framework
#+DESCRIPTION: A tasty hasty framework

* Fun with WebAssembly
  The Elm Architecture is a wonderful means for creating web apps without worrying about runtime errors, Hastea is a TEA-inspired web framework using those principles on top of Haskell compiled to WebAssembly with [[https://ghc.gitlab.haskell.org/ghc/doc/users_guide/wasm.html][GHC's WebAssembly backend]].

  (Hastea originally targeted Asterius, which has since been superseded by the wasm backend in mainline GHC.)

* Layout
  | ~src/~              | The ~hastea~ library (~Hastea.App~, ~Hastea.Cmd~, ~Hastea.Decode~, ~Hastea.Async~): the runtime and virtual DOM |
  | ~hastea-html/~      | The ~hastea-html~ sublibrary and its tests: HTML elements, attributes, events and decoders. No JavaScript     |
  | ~examples/todomvc/~ | The TodoMVC example executable, with its static files in ~www/~                                               |
  | ~build.sh~          | Builds the example into ~dist/~                                                                               |

* Writing views
  ~hastea-html~ has a function for every element of the HTML standard, plus their attributes and events. It is a sublibrary of the ~hastea~ package, which re-exports its modules, so depending on ~hastea~ is enough. (To use the view layer alone, depend on ~hastea:hastea-html~.)

  #+BEGIN_SRC haskell
  import Prelude hiding (div)

  import Hastea.Html
  import Hastea.Html.Attributes (className, disabled, placeholder, value)
  import Hastea.Html.Events (onClick, onInput)

  view :: Model -> Html Msg
  view model =
    div
      [className "signup"]
      [ input [placeholder "Your name", value (name model), onInput NameChanged]
      , button [onClick Submit, disabled (null (name model))] [text "Sign up"]
      ]
  #+END_SRC

  | ~Hastea.Html~            | Elements. Void elements such as ~input~ and ~br~ take only attributes                         |
  | ~Hastea.Html.Attributes~ | Attributes, and helpers such as ~classList~, ~styles~, ~dataAttr~ and ~aria~                  |
  | ~Hastea.Html.Events~     | Event handlers; ~on~ and ~onWith~ for custom ones                                             |
  | ~Hastea.Html.Decode~     | Decoders for reading event data                                                               |
  | ~Hastea.Html.Render~     | ~renderHtml~, which turns a view into a string of markup, for tests and server-side rendering |

  Some names exist both as an element and as an attribute (~title~, ~style~, ~form~, ~label~, ...), so import ~Hastea.Html.Attributes~ qualified or with an import list.

* How rendering works
  The design follows React, and leans on purity where Haskell allows more.

  - *Rendering is split into a pure and an effectful half.* ~Hastea.Html.Diff.diff~ compares the tree on the page with the new one and returns a ~Patch~: a description of what to change. Only ~Hastea.Internal.Commit~ touches the DOM, by carrying the patch out. The pure half is tested without a browser.
  - *Event handlers are data, not DOM listeners.* Nothing is attached to the elements of a view. The root listens for each kind of event once; when one arrives it locates the target in the tree it last rendered and runs the handlers found there and on its ancestors. Handlers can therefore never be out of date, and changing one costs nothing.
  - *Renders are batched.* Messages update the model immediately, but the view is shown at most once per frame.
  - *~keyed~* gives a child an identity, so that reordering or filtering a list moves DOM nodes instead of rebuilding them.
  - *~lazy~* skips a subtree whose inputs are the same values in memory as last time. Because views are pure this is always safe, and the skipped view is not even computed.

  ~Hastea.App.runApp~ is the Elm-style loop (model, update, view). It is a thin layer over ~Hastea.Root~ (~mount~ and ~render~), which only shows trees and reports messages, and can serve as the base for other architectures.

* Building
** Get the wasm toolchain
   You need the ~wasm32-wasi-ghc~ cross-compiler and ~cabal~ from [[https://gitlab.haskell.org/haskell-wasm/ghc-wasm-meta][ghc-wasm-meta]]. Either:

   - With Nix:
     #+BEGIN_SRC bash
     nix shell 'gitlab:haskell-wasm/ghc-wasm-meta?host=gitlab.haskell.org'
     #+END_SRC
   - Without Nix (x86_64/aarch64 Linux, macOS):
     #+BEGIN_SRC bash
     curl https://gitlab.haskell.org/haskell-wasm/ghc-wasm-meta/-/raw/master/bootstrap.sh | sh
     source ~/.ghc-wasm/env
     #+END_SRC
     The script needs ~curl~, ~jq~, ~unzip~, ~zstd~ (for ~unzstd~), ~xz~, ~make~ and a C compiler; it stops partway if one is missing, and can simply be run again. On Debian/Ubuntu:
     #+BEGIN_SRC bash
     sudo apt-get install curl jq unzip zstd xz-utils make gcc
     #+END_SRC
     It installs into =~/.ghc-wasm=. Run ~source ~/.ghc-wasm/env~ in every new shell to put the tools on your ~PATH~.

   Both routes download prebuilt binaries from GitHub releases, so they need access to ~github.com~ as well as ~gitlab.haskell.org~.

   Hastea is tested with the GHC 9.14 flavour.

** Build, test and run
   Everything is one cabal package (~hastea.cabal~), built with ~wasm32-wasi-cabal~, the cabal wrapper that comes with the toolchain:

   #+BEGIN_SRC bash
   wasm32-wasi-cabal test               # build everything and run the tests
   ./build.sh                           # build the example into dist/
   python3 -m http.server -d dist 8080  # then open http://localhost:8080
   #+END_SRC

   The tests cover ~hastea-html~ and run under ~wasmtime~, which is part of the toolchain.

   The example page fetches [[https://github.com/bjorn3/browser_wasi_shim][browser_wasi_shim]] from jsDelivr when it loads, so the browser needs internet access.

   If you have your own ~cabal~ on your ~PATH~ it works in place of ~wasm32-wasi-cabal~, since ~cabal.project~ selects the wasm compiler; for the example, run ~CABAL=cabal ./build.sh~.

* Development
  - Formatting: [[https://github.com/fourmolu/fourmolu][fourmolu]], configured in ~fourmolu.yaml~.
    #+BEGIN_SRC bash
    fourmolu -i src hastea-html examples
    #+END_SRC
  - Editor support: ~hie.yaml~ points HLS at the cabal components. HLS has to be able to load the project with the wasm compiler for this to work.
  - The code builds warning-free under ~-Wall -Wcompat~.
